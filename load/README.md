# Нагрузочный тест второго этапа

Сервис заявок, вариант 2, префикс nikita_zozulenko. k6 1.3.0.

| Операция | Вес, % | Обоснование |
|---|---:|---|
| Категории | 5 | Справочник открывают при выборе темы обращения. |
| Список заявок | 30 | Основной экран сотрудника поддержки. |
| Список новых заявок | 15 | Сотрудник выбирает обращения, которые ещё не взяты в работу. |
| Карточка заявки | 25 | Переписку читают перед ответом и изменением статуса. |
| Создание заявки | 8 | Новые обращения появляются реже просмотров существующих. |
| Комментарий | 8 | Переписка пополняется во время обработки обращений. |
| Изменение статуса | 7 | Сотрудник отмечает начало работы над заявкой. |
| Сводка | 2 | Руководитель обращается к общей статистике реже, чем сотрудники к заявкам. |

Сумма весов — 100 %. На каждые 100 начатых итераций профиль повторяется точно.
Короткая серия может немного отличаться от этих долей.

Режимы MODE=mixed и MODE=heavy: открытая модель constant-arrival-rate, одна
итерация — один бизнес-запрос. RATE — запросов в секунду; DURATION — длительность
в секундах (например, 30s). MODE=heavy вызывает только GET /api/summary.
Вход demo выполняется один раз в setup; пользовательские метрики business_*
не включают вход. Порог: p95 < 500 мс и ошибки < 1 %. HTTP 409 считается ожидаемым
только вместе с соответствующим кодом бизнес-отказа из контракта.

MODE=smoke последовательно проверяет все восемь видов запросов, без оценки
производительности. Перед каждой измеряемой ступенью повторить seed.py work.
Не запускать другие измерения одновременно. Между ступенями дождаться простоя.

Пример из корня репозитория, при запущенном docker compose:

```sh
docker compose exec api python seed.py work
mkdir -p results/dz2
docker run --rm --network nikita_zozulenko_default \
  -v "$PWD:/work" -w /work \
  -e MODE=mixed -e RATE=2 -e DURATION=30s \
  -e RESULT=/work/results/dz2/mixed-2.json \
  grafana/k6:1.3.0 run load/test.js
```

VUS по умолчанию 100, пул фиксирован, динамического выделения VU нет. Нехватку
VU видно по dropped_iterations. Каждый завершённый запрос, включая ошибку,
учитывается в business_completed. Фактическая частота — число завершённых
бизнес-запросов, делённое на длительность ступени с учётом завершения хвоста;
время setup не учитывается. Результат RESULT сохраняет сводку и исходные метрики.
Отдельные ошибки печатаются с операцией, HTTP-кодом и телом ответа.

Приложение работает в исходном режиме: один worker и один thread.
Индексы, кеширование и бизнес-код в рамках подготовки теста не менялись.
